## 1. 项目目标与范围

「今天你双休了吗？」是一个**纯静态**网站，用公司/学校两个板块收集并展示「是否真的双休」的信息。

| 板块 | URL 参数 | 数据源 | 内容 |
|------|----------|--------|------|
| 公司板块 | `board=companies` | `data/companies.json`（+ 超限分片） | 公司 = 名称 / 类别 / 岗位（岗位名称 · 双休 · 八小时工作制 · 情况）/ 备注 / 评价 |
| 学校板块 | `board=schools` | `data/schools.json`（+ 超限分片） | 学校 = 名称 / 双休情况 / 补课情况 / 评价 |

范围（In Scope）：

- `web/`：纯静态前端（按键渲染、搜索、排序、状态筛选、四类状态、无障碍、响应式、深色模式）。
- `data/`：`index.json`（索引与上限）+ `companies.json`（由根目录 `data.txt` 转换而来的真实公司数据，36 家 / 100 条岗位）+ `schools.json`（当前为空数组）；超限时才出现 `companies-N.json` / `schools-N.json`。
- `add_prog/`：Python + tkinter 可视化编辑器（公司/学校增删改、岗位与评价子表、上限校验与拆分辅助）。
- `README.md`：面向访客/贡献者的使用、数据与部署说明。

非范围（Out of Scope）：

- 后端服务、数据库、用户登录、真实提交接口、数据抓取。
- 构建工具链（webpack/vite/npm 依赖）、前端框架、CSS 预处理器。
- 任何需要联网 CDN 才能渲染的核心功能（**零外链**，必须离线可用）。

**v1.2.1 数据现状（重要）**：仓库根目录 `data.txt`（356 行）是用户手写的**真实基础数据**；`data/companies.json` 是它的转换产物，当前装载 **36 家公司 / 100 条岗位**（字段为 `名称` / `类别` / `岗位[{岗位名称, 双休, 八小时工作制, 情况}]` / `备注` / `评价`）。`data/schools.json` 仍为 `{"学校": []}`（`data.txt` 不含学校数据）。`data/index.json` 必须写全 `version`、`limits`、`companies`、`schools` 四个键。
>
> **默认状态必须展示这些真实数据，不得出现空白页**；空状态样式仍然保留，供数据被清空（数组为 `[]`）时使用。

> 原始需求（README 附录）中「公司名称 / 经营范围 / 主要职业 / 是否双休 / 介绍 / 其他信息 / 评价」等逐字段要求，自 v1.1 起已由本文件第 3 节的数据模型取代，v1.2.1 再次修订为 §3.4 的公司/学校字段表；README 附录中的原始提示词仍须原样保留（见 §6 第 10 条）。

冻结要点（**约定，不得变更**）：

- 文档与代码中的路径一律为 **POSIX 相对形式**（`data/companies.json`），不写盘符或反斜杠。
- 所有文本文件编码 **UTF-8（无 BOM）**；换行 LF 或 CRLF 均可，但同一文件内保持一致。
- `data/` 下**只允许**出现 `index.json`、`companies.json`、`schools.json`，以及 §3.6 规定、且已被 `index.json` 列出的分片 `companies-N.json` / `schools-N.json`；不得出现任何其它文件（含 `.gitkeep`、`README`、旧省份文件）。
- 根目录 `data.txt` 是**转换输入**（用户手写），不是站点资源：站点运行时不读取它，只由 §3.5 的转换规则与编辑器/脚本使用。
- **纯静态 + GitHub Pages（冻结）**：不得依赖任何服务器端能力（无后端、无 API、无构建、无重写规则）；所有资源请求一律**相对路径**，**不得以 `/` 开头**。

### 2.1 仓库根 `index.html`（发布入口，冻结标记）

GitHub Pages 默认以仓库根 `index.html` 为入口；它只做跳转，不承载业务逻辑、不写死数据。下列两个要素**必须存在**（允许附加注释、样式与 `class` / `id` / `rel` 等属性）：

```html
<meta http-equiv="refresh" content="0; url=web/index.html">
<a href="web/index.html">点击这里进入</a>
```

- `meta`：`http-equiv="refresh"` 与 `content="0; url=web/index.html"` 必须**逐字出现**；
- 手动链接：必须存在一个指向 `web/index.html` 的相对链接 —— 即 `<a … href="web/index.html">`（`class` / `id` / `rel` 等属性可任意附加，文案可自定）。

发布地址形如 `https://<user>.github.io/<repo>/`，跳转后为 `https://<user>.github.io/<repo>/web/index.html`；页面内对 `data/*.json`、`styles.css`、`app.js`、`data-snapshot.js` 的引用必须是**相对于当前页面**的相对路径（如 `../data/index.json`、`styles.css`）。

### 2.2 路径与部署规则（冻结）

- `web/index.html` 中的所有资源引用**不得以 `/` 开头**；发布到仓库子路径（如 `https://<user>.github.io/<repo>/web/index.html`）后必须同样可用。
- `web/index.html` 必须**先引入** `data-snapshot.js`、**后引入** `app.js`（保证 `file://` 兜底数据先于逻辑可用，见 §4.3）。
- 不得依赖任何 HTTP 头、重写规则、代理、CORS 配置或后端接口；`file://`、`http://localhost:8000/...`、`https://<user>.github.io/<repo>/...` 三种打开方式都必须能工作（`file://` 走离线快照）。
- 发布方式：GitHub 仓库 Settings → Pages → Source 选择分支与目录（推荐 `/ (root)`，根 `index.html` 即入口）；README 必须写明该步骤与访问地址（见 §6 第 8 条）。

### 2.3 已废弃：v1.1 的目录契约（34 个省份文件 + 城市冻结表）

v1.1 曾规定 `data/` 下 34 个省份文件（`beijing.json` … `taiwan.json`）、省级清单 `data/manifest.json`、`data/enterprises.json`，并在其 §2.2 冻结「34 个省级行政区 / 466 个城市键」的城市表。**以上目录契约自 v1.2 起全部废弃，对应文件必须从仓库中删除**（逐条对照见 §3.8）。

**废弃原因**：用户第三次需求变更 —— 数据改为按「公司 / 学校」集中收集的**扁平结构**，不再按「省份 → 城市」组织；地区层级带来的 34 个文件与 466 个城市键既无法承载公司/学校字段表，也显著增加录入与维护成本。

## 3. 数据规格

### 3.1 `data/index.json`（索引与上限，冻结）

前端**只读 `index.json`** 来决定加载哪些分片；它是数据目录的唯一入口清单。

```json
{
  "version": 1,
  "limits": { "maxRecordsPerFile": 100, "maxBytesPerFile": 262144 },
  "companies": ["companies.json"],
  "schools": ["schools.json"],
  "comments": ["comments.json"],
  "site": { "repo": "OWNER/REPO", "issueLabel": "comment-submission" }
}
```

| 键 | 类型 | 语义与约束 |
|----|------|------------|
| `version` | number | 索引格式版本，v1.2.1 固定为 `1` |
| `limits` | object | 单文件上限对象：`{ "maxRecordsPerFile": 100, "maxBytesPerFile": 262144 }` |
| `limits.maxRecordsPerFile` | number | 单文件**记录数**上限：固定 `100`（一条记录 = `公司` / `学校` 数组的一个元素） |
| `limits.maxBytesPerFile` | number | 单文件**字节数**上限（按该文件 UTF-8 实际字节数计）：固定 `262144`（256 KB） |
| `companies` | string[] | 公司分片的**文件名数组**，数组顺序 = 加载顺序；未拆分时恰为 `["companies.json"]` |
| `schools` | string[] | 学校分片的文件名数组，同上；未拆分时恰为 `["schools.json"]` |
| `comments` | string[] | 评论分片的文件名数组，规则同 `companies` / `schools`；未拆分时恰为 `["comments.json"]`（§3.9） |
| `site` | object | 站点与提交配置：`{ "repo": "OWNER/REPO", "issueLabel": "comment-submission" }` |
| `site.repo` | string | GitHub 仓库 `OWNER/REPO` 形式；**发布前必须由用户改成自己的仓库**；仍为占位值 `OWNER/REPO` 时前端禁用评论提交并提示（§4.7） |
| `site.issueLabel` | string | 评论 Issue 的标签名，**固定为 `comment-submission`**，与 Action 的触发条件一致 |

约束：

1. 上述六个顶层键（`version` / `limits` / `companies` / `schools` / `comments` / `site`）**必须全部存在**，不得增减；表中所列值与类型**逐字冻结**，不得自行替换。
2. `companies` / `schools` / `comments` 必须是非空数组，元素为 `data/` 下的**文件名**（不含目录前缀、不含 `..`、不以 `/` 开头）。
3. **`index.json` 列出的分片文件必须真实存在**，且 `data/` 下不得存在未被列出的分片或其它文件（由 V2 校验）。
   - `site.repo` 必须是 `OWNER/REPO` 形式（含一个 `/`）；`site.issueLabel` 必须逐字为 `comment-submission`（由 V12 校验）。
4. `index.json` 的 `companies` 字段是**分片文件名数组**，属 v1.2 起的新契约；与 §3.8 中已废弃的 v1.0 省份文件顶层数组键 `companies` **无任何关系**，不得混淆。
5. UTF-8 无 BOM，JSON 必须合法。

### 3.4 条目字段表（冻结）

**公司条目**（`data/companies.json` → `公司[]`）：

| 键 | 类型 | 必填 | 取值 / 说明 |
|----|------|------|-------------|
| `名称` | string | 是 | 公司名称，非空，长度 1–80；同一文件内唯一 |
| `类别` | string | 是 | 四类枚举之一：`制造业` / `消费零售·餐饮` / `新能源汽车` / `互联网·科技` |
| `岗位` | object[] | 是 | **非空**数组，元素为岗位对象（见下表） |
| `备注` | string | 否 | 承载 `data.txt` 中该公司的「负面 / 负面舆情」正文（去引用符号与「负面：/负面舆情：」前缀）；无则省略 |
| `评价` | object[] | 否 | 评价子表，元素为 `{ "编号": number, "内容": string }`；当前为空，可省略 |

> **公司级没有状态字段（冻结）**：`双休` / `八小时工作制` **只存在于岗位子层**；公司条目**没有也不要求** `休息情况` 字段（该字段已于 §3.8 废弃）。公司级的状态展示由前端按 §4.6 的规则**推导**得出，不写回数据。学校条目的 `双休情况` 则保留为公司级字段（见下表）。

**岗位对象**（`公司[].岗位[]`）：

| 键 | 类型 | 必填 | 取值 / 说明 |
|----|------|------|-------------|
| `岗位名称` | string | 是 | 非空，如「技术研发岗 (后台/客户端/前端/算法等)」 |
| `双休` | string | 否 | 枚举：`是` / `否` / `未知`；无法机械判定时**省略**（原文仍在 `情况` 中） |
| `八小时工作制` | string | 否 | 枚举：`是` / `否` / `未知`；无法机械判定时**省略** |
| `情况` | string | 否 | `data.txt` 中该岗位描述的**原文**（可去首尾空白，不得截断或改写） |

**学校条目**（`data/schools.json` → `学校[]`）：

| 键 | 类型 | 必填 | 取值 / 说明 |
|----|------|------|-------------|
| `名称` | string | 是 | 学校名称，非空，长度 1–80 |
| `双休情况` | string | 是 | 自由文本（如「周末正常双休」「高三单休」），不得为空字符串 |
| `补课情况` | string | 否 | 自由文本；缺省时该行不渲染 |
| `评价` | object[] | 否 | 同公司评价子表 |

通用约束：

1. **允许出现表外的新键**（前向兼容）：前端按键渲染，新增键无需改动任何代码即可显示（§4.2）。表中「必填」约束编辑器与录入规范，不约束前端渲染的容错。
2. 同一文件内 `名称` 不得重复；同一父条目内 `评价.编号` 从 1 起连续递增。
3. **同一公司内 `岗位名称` 必须唯一** —— 这是 §3.5 D3「同名岗位合并去重」的**依据**：公司在 `data.txt` 中出现两次时，同名岗位必须合成一条（例：美团·外卖骑手、赵一鸣·管理层）。**跨公司出现同名岗位不受限制**（例：多家公司都有「管理层」「研发岗」），不得因此报错或合并。
4. `双休` / `八小时工作制` 只允许 `是` / `否` / `未知`；**「省略」与 `未知` 语义不同** —— 省略 = 无法从原文机械判定；`未知` = 原文明确表示未知/不确定。
5. 数据内容保持中性：保留用户 `data.txt` 的原始表述，不得新增指控或改写原文（§6 第 9 条）。
6. 同一数组内所有条目必须是**对象**；出现字符串、数字或 `null` 作为条目即视为非法数据，编辑器与校验命令必须拒绝。

> **`双休` / `八小时工作制`：「省略」与「`未知`」对前端**语义等价**（冻结）** —— 两者都表示「原文未提供足够信息」；差别仅在渲染：字段**缺失**（省略）时该行不渲染，显式取值 `未知` 时渲染中性标签。§3.5 C 的「未命中关键词则省略字段」与 data-core 现有产物统一写 `未知` **两者都合法、互不矛盾**；前端必须同时容错，且**不得**把缺失或 `未知` 当作 `是` / `否`。

### 3.5 数据来源与转换规则（`data.txt` → `data/companies.json`，冻结）

`data.txt`（仓库根目录，356 行）是用户手写的**唯一真实数据源**；`data/companies.json` 是它的转换产物。转换必须**机械、可复现、零丢失**。

**A. 文档结构**

| 片段 | 形态 | 转换结果 |
|------|------|----------|
| 分组标题 | 以 🏭 / 🛒 / 🚗 等符号开头的整行 | 该段公司的 `类别`：`制造业` / `消费零售·餐饮` / `新能源汽车`。**规范化规则**：去掉符号与首尾空白，并把标题中的 `/` 一律写成 `·`（源文件写作「🛒 消费零售/餐饮」，产物写作 `消费零售·餐饮`） |
| 无标题前段 | 第一个分组标题之前的散文段公司（腾讯 … 联想） | `类别` 统一记为 `互联网·科技` |
| 模板段 | `名称，{岗位名:{双休:X}{八小时工作制:Y}{备注:Z}}…` | 该公司的一个或多个岗位（见 B） |
| 散文段 | 公司名整行 + 若干 `岗位线索：描述。` 行 | 该公司的一个或多个岗位（见 C） |
| 负面行 | 模板段的 `> 负面舆情：…`、散文段的 `负面：…` | 公司级 `备注`（见 D） |

**B. 模板段（`data.txt` 第一部分，蜜雪冰城 / 赵一鸣 / 美的 / 美团 / 阿里巴巴）**

1. 逗号（`，`）前的文本 = `名称`；其后的每个顶层 `{…}` = 一个岗位（如 `{奶茶店员工:…}{管理层:未知}` = 2 个岗位）。
2. 岗位值形如 `{双休:否}{八小时工作制:否}{备注:…}`：`双休`、`八小时工作制` 直接填入 `是` / `否` / `未知`；`备注` 的内容填入该岗位的 `情况`。
3. 岗位值若是**标量**（如 `{管理层:未知}`），该标量解释为 `双休` 的取值，其余字段省略。
4. 紧随其后的 `> 负面舆情：…` 行 → 公司级 `备注`。

**C. 散文段（`data.txt` 第二部分）**

1. 每个 `岗位线索：描述。` 行 = 一个岗位：**全角冒号前**的文本 = `岗位名称`（去首尾空白）；**冒号后的完整原文** = `情况`（可去首尾空白，**不得截断、改写或丢弃**）。
2. `双休` / `八小时工作制` 只在描述命中下列**字面关键词**时填写；判定顺序为「否 → 是 → 未知」，命中即停；都不命中则**省略该字段**（不做语义推断）：
   - `双休` = `否`：`单休` / `大小周` / `做六休一` / `月休` / `无固定双休` / `无正常双休` / `无双休`
   - `双休` = `是`：`周末双休` / `做五休二` / `双休` / `5天8小时` / `取消大小周`
   - `双休` = `未知`：`轮班` / `轮休` / `排班` / `综合计算` / `未明确` / `未标注`
   - `八小时工作制` = `否`：`12小时` / `11小时` / `10.5小时` / `9小时` / `不足8小时`
   - `八小时工作制` = `是`：`8小时工作制` / `八小时工作制` / `5天8小时` / `全职8小时` / `每天8小时` / `基本8小时`
3. 行首为 `负面：…` 的整行（含「公开渠道中鲜有负面舆情。」这类表述）→ 公司级 `备注`。

**D. 备注与去重合并**

1. `备注` = 负面正文：去掉 `>` 引用符号与「负面：」「负面舆情：」前缀，正文原样保留。
2. **公司级合并**：按 `名称` 合并 —— `data.txt` 中 `蜜雪冰城` / `赵一鸣` / `美的` / `美团` / `阿里巴巴` 各出现两次（模板段 + 散文段）；合并后 `名称` 必须唯一，`备注` 多段时按出现顺序以换行拼接。
3. **岗位级合并（同名岗位去重）**：同一公司内 `岗位名称` **完全相同**的岗位合并为一条 —— `情况` 多段以换行拼接（模板段在前、散文段在后，**不得丢弃任何一段原文**，例：美团·外卖骑手）；`双休` / `八小时工作制` 以**散文段（后出现者）**的判定为准，散文段缺该字段时回退到模板段取值（例：赵一鸣·管理层）。当前共 2 组同名岗位（美团·外卖骑手、赵一鸣·管理层）。
4. **岗位顺序**：合并后的 `岗位` 数组顺序 = 该公司岗位在 `data.txt` 中的出现顺序（模板段在前、散文段在后；同名合并保留首次出现的位置）。
5. `类别` 取该公司在散文段所属分组的标题（按 A 表的规范化规则处理，**必须落在 §3.4 的四类枚举内**，例如标题「消费零售/餐饮」→ `消费零售·餐饮`）；散文段无标题的前段记为 `互联网·科技`；仍无法判定时同样记为 `互联网·科技`（`类别` 必填）。

**E. 期望计数（机械统计，由 V3 校验）**

| 指标 | 期望值 |
|------|--------|
| 公司数（去重后） | **36** |
| 岗位条目数 | **100**（模板段 10 + 散文段 92 − 同名岗位合并 2） |
| 类别分布 | `互联网·科技` 14 / `消费零售·餐饮` 14 / `制造业` 5 / `新能源汽车` 3 |
| 备注（负面）段数 | 41（模板段 5 + 散文段 36） |
| 公司级合并（跨两段） | 蜜雪冰城、赵一鸣、美的、美团、阿里巴巴 |
| 岗位级合并（同名岗位） | 美团·外卖骑手、赵一鸣·管理层（共 2 组） |

**F. 零丢失原则（冻结）**

1. 每家公司的岗位条目数必须等于 `data.txt` 中该公司「内联岗位组 + 岗位行」的数量**减去同名岗位合并数**（当前 102 − 2 = **100**）；合并前后均不得丢弃任何原文段落。
2. 每个岗位的 `情况` 必须是 `data.txt` 对应描述的原文；`双休` / `八小时工作制` 未命中关键词时**省略字段**，但原文**必须**留在 `情况` 中 —— **字段缺失绝不等于原文丢失**。
3. 每段「负面 / 负面舆情」正文都必须落到某家公司的 `备注`（可多段换行拼接），不得丢弃。

### 3.6 上限与拆分规则（冻结）

1. **上限**：单个数据文件（含 `companies.json` / `schools.json` 与任一分片）必须同时满足 —— 记录数 ≤ `limits.maxRecordsPerFile`（100）且文件字节数 ≤ `limits.maxBytesPerFile`（262144）；**先到为准**，任一超限即必须拆分。
2. **何时拆分**：当 `companies.json`（或 `schools.json`）将要写入第 101 条记录，或文件字节数将超过 262144 时，必须拆分为 `companies-1.json`、`companies-2.json`…（学校同理 `schools-N.json`）。当前 36 家公司 / 100 条岗位，**尚未触发拆分**。
3. **拆分方式（冻结）**：拆分是把原文件的**全部记录**按原顺序重新分配到各分片，且**每个分片自身也必须 ≤ 上限**（规则 1）。拆分完成后，**原 `companies.json` / `schools.json` 不再存在**（不允许保留无编号文件作为别名或封面）。
4. **命名与顺序（冻结）**：分片文件名固定为 `<base>-N.json`（`base` 为 `companies` 或 `schools`；`N` 从 `1` 起连续递增、无前导 0）；`index.json` 中对应数组**必须按加载顺序逐个列出全部分片**，即 `["companies-1.json", "companies-2.json", …]`。未拆分时，文件名必须是不带编号的 `companies.json` / `schools.json`。
5. **同步更新索引**：拆分、合并或删除分片后，必须同步更新 `index.json` 的 `companies` / `schools` 数组，保证「索引内容 = `data/` 下真实分片集合 = 加载顺序」三者一致（由 V2 / V4 校验）。
6. **前端行为**：前端只按 `index.json` 的数组顺序拉取并合并（`公司` 数组按分片顺序 `concat`，学校同理）；页面行为不得依赖分片数量，也不得硬编码任何分片名。

### 3.7 结构约定、空值语义与编码

- **结构约定（冻结）**：`data/companies.json` 顶层固定 `{"公司": [...]}`、`data/schools.json` 顶层固定 `{"学校": [...]}`；`index.json` 四个键必须写全。
- **空数组 `[]` 是合法形态**：结构约定允许数组为空（当前 `schools.json` 即为空）；此时前端显示空状态而不是报错。**公司数据当前非空**（36 家公司 / 100 条岗位），是站点的默认展示内容。
- **不设「必须先清空数据」之类的交付要求**：任何章节都不得要求 `companies.json` 保持为空。
- 三个文件编码 **UTF-8（无 BOM）**，且必须可被 `JSON.parse` 解析。
- 站点在数据为空与非空两种状态下都必须正常工作：非空时默认展示真实数据（不得空白页）；为空时显示空状态、计数 0、不抛错、不白屏。
- 将来追加数据时必须遵守 §3.4 字段表与 §3.5 转换规则、§3.6 上限/拆分规则；示例内容需带「演示数据」字样。

### 3.9 `data/comments.json`（评论数据，冻结）

评论是**独立数据文件**：评论**不写进** `companies.json` / `schools.json`，而是靠 `板块` + `目标` 两个字段**与条目解耦地关联**（`目标` = 该条目的 `名称`）。同一个 `目标` 名称可以在不同板块各有一条关联（如「公司:腾讯」与「学校:腾讯」互不影响）。

顶层**只能有一个键** `评论`：

```json
{
  "评论": [
    { "编号": 1, "板块": "公司", "目标": "腾讯", "内容": "演示评论：周末确实双休。", "昵称": "octocat", "日期": "2025-01-15" }
  ]
}
```

当前交付为**空骨架**（合法形态）：`{ "评论": [] }`。

| 键 | 类型 | 必填 | 取值 / 说明 |
|----|------|------|-------------|
| `编号` | number | 是 | **全局自增、唯一、从 1 连续**（1..N 无缺口）；新增时 = 现有最大 `编号` + 1 |
| `板块` | string | 是 | 只允许 `公司` 或 `学校`（与 URL 的对应关系：`公司` ↔ `board=companies`、`学校` ↔ `board=schools`） |
| `目标` | string | 是 | 对应条目的 `名称`，非空；**必须**能在 `data/companies.json`（板块=公司）或 `data/schools.json`（板块=学校）中找到**同名条目** |
| `内容` | string | 是 | 评论正文，**1–1000 字**（按 Unicode 字符计；去首尾空白后必须非空） |
| `昵称` | string | 否 | 长度 ≤ 40；缺省时前端显示「匿名」；Action 落盘时**表单值优先，表单为空则取 Issue 作者（GitHub 用户名）** |
| `日期` | string | 否 | `YYYY-MM-DD`；**由 Action 落盘时自动填当天**，前端不填 |

约束：

1. 顶层固定 `{"评论": [...]}`，不得出现其它顶层键；空数组是合法形态（当前为空）。
2. 同一文件内 `编号` 不得重复、不得跳号（`1..N` 连续）；展示与写入一律按 `编号` 升序。
3. **目标必须存在**：`板块` + `目标` 必须命中一条现有条目，否则视为非法/孤儿评论 —— 前端忽略其展示（不报错），Action 拒绝写入，V11 报错要求人工清理（条目被删除时需同步清理评论）。
4. UTF-8 无 BOM；JSON 必须合法；内容保持中性，不得写入违法、辱骂或他人隐私信息。
5. **上限与拆分**：`comments.json` 同样受 §3.6 约束（>100 条记录或 >262144 字节即拆为 `comments-1.json`、`comments-2.json`…，并把 `index.json.comments` 按加载顺序列出全部分片）。
6. **落盘方（GitHub Action）**：见 §4.7 的 Issue 模板与 §6 第 11 条的启用步骤；Action 必须校验 `板块` / `目标` 存在 / `内容` 1–1000 字，非法则拒绝写入并在 Issue 上说明。

### 4.2 按键渲染（数据驱动）规则 —— 冻结

**总则**：前端必须完全「按键渲染」。页面**不得写死**任何公司名、学校名、字段名或枚举清单；所有标题、分组与条目都必须由 JSON 的**键与值**动态生成。

| JSON 值形态 | 渲染方式（冻结） |
|-------------|------------------|
| 对象 `{...}` | **分组递归**：每个键 → 分组标题，值 → 递归渲染 |
| 数组（元素为对象） | **条目列表**：逐条递归渲染 |
| 数组（元素为标量） | 逐条渲染为一行标量文本 |
| 字符串 | 「**键: 值**」行；数组中不带键的标量直接渲染该值 |
| 数字 | 「**键: 值**」行（保留原值，不做四舍五入） |
| 布尔 | 「键: 是」/「键: 否」 |
| `null` | 「键: 未知」 |
| 空数组 `[]` / 空对象 `{}` | 该层级的**空状态**（如「暂无记录」），**不得报错**，不得渲染出 `undefined` / `NaN` / 空白 |

**约定键的增强呈现（冻结）** —— 仅用于视觉增强；键缺失时功能不受影响。

| 键 | 呈现方式 |
|----|----------|
| `名称` | 条目主标题；条目无 `名称` 时取第一个标量值，仍无则显示「未命名」 |
| `类别` | 类别徽标（`制造业` / `消费零售·餐饮` / `新能源汽车` / `互联网·科技`；其它取值按原文渲染） |
| `岗位` | 子列表：每项渲染 `岗位名称` + `双休` + `八小时工作制` + `情况`；岗位内缺失的字段该行不渲染 |
| `双休` | 状态标签：`是` / `否` / `未知`。取值为 `是` / `否` 时**必须「颜色 + 文字」双重区分** —— 文字标签始终可见，颜色仅作辅助，**不得只靠颜色传递语义** |
| `八小时工作制` | 同 `双休`：`是` / `否` / `未知`，是/否 必须「颜色 + 文字」双重区分 |
| `情况` | 「情况: 值」行（长文本换行展示，不得截断） |
| `备注` | 引用样式段落（承载负面舆情），带「备注」文字标签 |
| `评价` | 引用样式列表：`编号` + `内容` |
| `双休情况` | 状态标签（学校板块；取值按原文渲染） |
| `补课情况` | 「键: 值」行（可与状态样式并列展示） |

**未约定的键一律回退为通用「键: 值」行**，不得丢弃、不得报错；新增键无需修改任何前端文件即可显示。

> §4.6 的公司级**推导状态**是前端计算值（不是数据键）：渲染为卡片级摘要标签时按本表的状态标签规则处理（文字 + 颜色，颜色仅辅助，且必须标注为「按岗位汇总」的推导值）。

**可验证推论（F3 / F4 的验收基础）**：

1. 往任意数据文件新增一个键（或往数组新增一条记录），刷新页面即可看到新内容，该过程**不修改任何前端文件**；
2. 公司与学校两个板块共用同一套递归渲染逻辑，差异只体现为数据源、约定键与文案，不体现为硬编码的名称或字段清单；
3. 数据为空（数组为 `[]`，如当前 `schools.json`）时页面不报错，并逐层显示空状态；数据非空时必须逐条展示真实条目，不得空白页。

### 4.3 数据加载、状态机与离线快照

**加载流程（`http(s)://`）**：

1. 请求 `data/index.json`（相对路径）。
2. 按 `index.companies` 的数组顺序请求各公司分片，并按同样顺序 `concat` 其 `公司` 数组；学校板块同理（`index.schools` → `学校`）。
3. 任一分片请求失败或 JSON 解析失败 → **加载失败状态**：显示明确错误文案 + 重试按钮（重试重新执行第 1–2 步），不得静默、不得白屏。
4. 加载期间显示**加载中状态**（骨架或文案）。
5. 加载完成后**默认渲染真实数据**（公司板块当前为 36 家 / 100 条岗位）；只有数据确为空数组时才进入空状态，**不得出现空白页**。

**离线兜底（`file://`）**：

- 直接双击打开 `web/index.html` 时，浏览器会因同源策略拒绝 `fetch`；此时必须回退到 `web/data-snapshot.js`，并在 `#state-region` 显示一条**醒目但不阻塞**的离线快照提示，说明如何用本地静态服务器查看真实数据（见 §6 第 4 条）。
- **快照契约（冻结）**：`web/data-snapshot.js` 是普通脚本（非模块），必须把「文件镜像」挂到 `window.SHUANGXIU_SNAPSHOT`：

```js
window.SHUANGXIU_SNAPSHOT = {
  "index.json": { /* 与 data/index.json 深等价（含 comments / site 两键） */ },
  "companies.json": { "公司": [ /* 与 data/companies.json 深等价：36 家公司 / 100 条岗位 */ ] },
  "schools.json": { "学校": [] },
  "comments.json": { "评论": [ /* 与 data/comments.json 深等价（当前为空数组） */ ] }
};
```

  - 键集合**必须**恰为 `index.json` 加上 `index.json` 中 `companies` / `schools` / `comments` 列出的全部分片文件名（`comments.json` **必须**一并镜像，见 §3.9）；
  - 每个键对应的值必须与该文件 `JSON.parse` 后的结果**深等价**（由 V10 校验）；
  - 数据变化后必须重新生成或同步快照（编辑器应在保存后提示，见 §5 E6）。
- 快照模式下，加载流程与上面第 1–2 步完全相同，只是数据来自 `window.SHUANGXIU_SNAPSHOT[文件名]` 而不是 `fetch`。
- `web/index.html` 必须在 `app.js` **之前**引入 `data-snapshot.js`（§2.2）。

**其它（冻结）**：禁止任何 CDN/外链脚本、字体、图片；无图标字体依赖；不得出现超过 1 秒的白屏（允许渐进式渲染）。

### 4.4 视觉与响应式

- 风格：简洁明快、卡片式，克制的强调色 + 中性灰阶，精致的中文排版（行高 ≥ 1.6）、细腻阴影圆角与微交互；**空状态**必须有可读文案与弱化色（数据为空时页面要像「完整的站点」而不是「坏了」）。
- 断点（冻结，至少覆盖三档）：
  - `< 640px` 移动端：单列布局；筛选控件纵向堆叠；可点击区域 ≥ 44px；
  - `640px – 1023px` 平板：一列或双列自适应网格；
  - `≥ 1024px` 桌面：多列网格（≥ 2 列）+ 顶部粘性工具栏。
- 使用 CSS Grid/Flex 与 `clamp()` 实现流式排版；任何一档**不得出现横向滚动条**。
- **深色模式**：跟随 `prefers-color-scheme: dark`；正文与状态标签（含 `双休` / `八小时工作制` 的 是/否 标签）对比度 ≥ 4.5:1，且深色模式下同样保持「颜色 + 文字」双重区分。
- **动效降级**：`prefers-reduced-motion: reduce` 时关闭非必要过渡与动画。

### 4.5 性能与兼容

- 目标浏览器：Chrome/Edge/Firefox/Safari 最近两个大版本；不使用需要转译的语法（ES2020 以内）。
- 无构建步骤：`web/` 中的文件可被直接托管或打开。
- 单页 DOM 节点数建议 < 3000；当前数据量小（36 家 / 100 条岗位）应即时渲染，不做无意义的分片等待。
- 分片合并后条目数可达数千条：渲染应避免一次性插入上万个节点（可用分页、懒渲染或文档片段），但不得因此跳过 F6–F10 的任何状态语义。

### 4.6 公司级状态推导（派生值，冻结）

公司级状态**只在前端计算中存在**，不写回 `data/`（数据里没有 `休息情况` 字段，见 §3.4）。推导输入 = 该公司 `岗位[]` 中每个岗位的 `双休` 取值（`是` / `否` / `未知` / 缺失）；按顺序判定，**先命中先返回**：

| 条件 | 推导值 |
|------|--------|
| 岗位中**同时存在** `是` 与 `否` | `部分双休` |
| 否则**存在** `是` | `全部双休` |
| 否则**存在** `否` | `无双休` |
| 否则（全部为 `未知` 或缺失，或 `岗位` 为空数组） | `未知` |

- 取值枚举固定为四项：`部分双休` / `全部双休` / `无双休` / `未知`；**不得增设第五项**，也不得把缺失或 `未知` 当作 `是` / `否`。
- 该推导值的用途（冻结）：①公司板块**状态筛选**（F8，控件 `#status-filter` 常驻）；②**排序**选项之一「状态」（F7，次序 `全部双休` → `部分双休` → `无双休` → `未知`，同级按名称升序）；③**统计与结果计数**（F9）；④公司卡片上的**公司级摘要标签**。
- 摘要标签必须**文字化并标注为推导值**（如「按岗位汇总：部分双休」），且不得只靠颜色区分；颜色仅作辅助。
- 当前真实数据的推导分布（供实现与评审核对）：`全部双休` 15 / `部分双休` 8 / `无双休` 12 / `未知` 1，合计 **36 家**。
- 岗位级 `双休` / `八小时工作制` 仍按 §4.2 在岗位子列表内渲染为状态标签（`是` / `否` 必须「颜色 + 文字」双重区分），并参与 F6 关键词搜索。

### 4.7 详情抽屉与评论提交（冻结）

#### 4.7.1 打开 / 关闭与 URL 深链

- 触发：卡片上的「更多信息」控件（`data-more="<条目名称>"`）。
- 打开：把 `entry=<名称>` 写入 URL 查询参数（保留现有 `board` / `q` / `sort` / `status`），使用 `history.pushState`；浏览器**后退 / 前进**必须能关闭 / 重新打开抽屉（监听 `popstate`）。
- 关闭：`Esc`、点击遮罩（overlay）、点击 `#drawer-close` 三种方式；关闭时移除 `entry` 参数（保留其它参数），并把焦点**回到触发按钮**。
- 深链：直接访问 `web/index.html?board=companies&entry=腾讯` 时必须自动打开对应抽屉；若该名称在当前板块数据中不存在 → 不打开，给出一次非阻塞提示并保持列表。
- 无障碍（冻结）：抽屉容器 `role="dialog"`、`aria-modal="true"`、`aria-labelledby` 指向抽屉标题；打开时把焦点移入抽屉（第一个可聚焦元素或 `#drawer-close`）；**焦点陷阱**：`Tab` / `Shift+Tab` 在抽屉内循环；关闭后焦点回到触发按钮；打开时页面其余内容对读屏隐藏（`aria-hidden` 或 `inert`）。

#### 4.7.2 抽屉内容

1. 条目**完整按键渲染内容**（§4.2）：公司 = `名称` / `类别` / `岗位` 块（每岗位 `岗位名称` + `双休` + `八小时工作制` + `情况`）/ `备注` / `评价`；学校 = `名称` / `双休情况` / `补课情况` / `备注` / `评价`。
2. 该条目的**评论列表**：取 `data/comments.json`（合并 `index.json.comments` 列出的全部分片）中 `板块` + `目标` 匹配当前条目的记录，按 `编号` 升序渲染（`昵称` 缺省显示「匿名」，`日期` 缺省不显示）；无评论时显示「暂无评论」。
3. **写评论表单**：`#comment-content`（textarea，必填，`maxlength="1000"`）+ `#comment-nickname`（可选，`maxlength="40"`）+ `#comment-submit` + `#comment-notice`。

#### 4.7.3 提交行为（预填 GitHub Issue）

提交**不直接写文件**：把表单内容拼成一条**预填的 GitHub Issue 链接**并在**新标签**打开（`rel="noopener"`），同时显示中文提示：**「需要 GitHub 账号，提交后由仓库的 GitHub Action 自动写入数据文件」**。

**Issue 模板（冻结，逐字稳定；Action 依此解析）**

title（一行，全角冒号）：

```text
[评论] <板块>：<目标>
```

例：`[评论] 公司：腾讯`（`<板块>` ∈ `公司` / `学校`；`<目标>` = 条目 `名称`）。

body：

```text
<!-- comment-submission -->
- 板块: 公司
- 目标: 腾讯
- 昵称: <昵称或 GitHub 用户名>
- 内容: <正文>
```

规则：**首行必须是 `<!-- comment-submission -->`**（HTML 注释标记，前后无空格）；随后四行必须逐字以「`- 板块: `」「`- 目标: `」「`- 昵称: `」「`- 内容: `」开头（半角冒号 + 一个半角空格）；`内容` 正文跟在「`- 内容: `」之后，可多行，Action 取该标记之后的**全部文本**并去除首尾空白。

链接形如：`https://github.com/<site.repo>/issues/new?title=<urlencoded title>&body=<urlencoded body>&labels=<site.issueLabel>`（`title` / `body` 必须经 `encodeURIComponent` 编码）。

**Action 触发与判定（冻结）**

- 工作流触发：`on: issues: [opened, labeled]` —— 覆盖「新建 Issue」与「后打标签」两条入口。
- 判定条件（满足其一即处理）：
  1. **Issue 正文包含固定标记 `<!-- comment-submission -->`** —— **这是主要判据**；
  2. Issue 带有 `site.issueLabel`（默认 `comment-submission`）标签 —— **辅助判据**，仅用于兼容「先建 Issue、后打标签」的场景。
- 两者都不满足 → **跳过**：不写入数据、不在 Issue 上评论、不关闭 Issue。
- 因为**标记是主要判据**，所以**即使用户尚未在仓库里创建 label，评论流程依然可用**（预填链接创建的 Issue 通常不带标签，靠正文标记即可命中）；因此 README 中「创建 label」的步骤是**推荐但非必需**。
- 命中后仍按 §3.9 约束 6 校验：合法则追加写入并回帖确认；非法则在 Issue 上说明（可选打失败标签 / 关闭）。

#### 4.7.4 表单校验（冻结）

1. `内容` 去首尾空白后**必须非空**且长度 **≤ 1000**（按 Unicode 字符计）；不满足时不得提交，并在 `#comment-notice` 给出中文提示。
2. `目标` 必须存在于当前板块数据（抽屉由条目打开，天然满足；若数据在打开后被替换导致不存在 → 拒绝提交并提示）。
3. `site.repo` 缺失或仍为占位值 `OWNER/REPO` → `#comment-submit` 必须为 `disabled`，`#comment-notice` 提示「需先在 data/index.json 的 site.repo 填写你的仓库」。
4. 提交后保留表单内容，并在 `#comment-notice` 提示「已打开 Issue 页面，请在 GitHub 上确认提交」。

#### 4.7.5 依赖与安全（冻结）

- **不得**引入任何第三方评论系统（Disqus / utterances / giscus 等）或外链脚本、外链字体；评论能力完全由「静态前端 + GitHub Issue + 仓库 Action」实现。
- 前端**只读**数据：任何用户输入都不得写入 `data/`（写入只发生在仓库的 GitHub Action 中，且必须通过 §3.9 约束 6 的校验）。
- 昵称与内容按**纯文本**渲染（`textContent` 或等价的转义），不得作为 HTML 注入（防 XSS）。

## 8. 术语与修订记录

- **公司条目**：`data/companies.json` 中 `公司` 数组的一个元素，字段为 `名称` / `类别` / `岗位` / `备注` / `评价`（见 §3.4）。当前共 36 家。
- **学校条目**：`data/schools.json` 中 `学校` 数组的一个元素，字段见 §3.4。
- **分片**：单文件超过上限时拆出的 `companies-N.json` / `schools-N.json`；加载顺序由 `index.json` 的数组顺序决定。
- **上限**：`limits.maxRecordsPerFile`（100 条记录）与 `limits.maxBytesPerFile`（262144 字节），先到为准。
- **按键渲染**：前端按 JSON 的键与值递归生成界面，不写死任何字段名或条目名（§4.2）。
- **空骨架**：`公司` / `学校` 数组为 `[]` 的**合法结构形态**（v1.2.1 仅作为结构约定保留，不再是交付要求；当前 `学校` 即为空数组）。
- **岗位条目**：公司条目的 `岗位` 数组元素，字段为 `岗位名称` / `双休` / `八小时工作制` / `情况`（见 §3.4）。当前共 100 条。
- **类别**：公司级四类枚举 `制造业` / `消费零售·餐饮` / `新能源汽车` / `互联网·科技`（§3.5 D）。
- **双休 / 八小时工作制**：岗位级三态枚举 `是` / `否` / `未知`；「省略」表示无法从原文机械判定（§3.5 C），与 `未知` 语义不同。
- **板块**：公司板块（`board=companies`）与学校板块（`board=schools`）；评论里的 `板块` 取值为中文 `公司` / `学校`。
- **评论条目**：`data/comments.json` 中 `评论` 数组的一个元素（`编号` / `板块` / `目标` / `内容` / `昵称` / `日期`）；与条目**解耦**，靠 `板块` + `目标`（= 条目 `名称`）关联（§3.9）。
- **详情抽屉**：卡片「更多信息」打开的全屏 overlay + panel 界面（F13 / §4.7），URL 深链 `?board=…&entry=…`。
- **Issue 提交模板**：评论提交用的 GitHub Issue 模板 —— title `[评论] <板块>：<目标>`，body 首行 `<!-- comment-submission -->` 加四行字段（§4.7.3）。
- **site.repo**：`data/index.json` 的 `site.repo`；发布前必须填自己的 `OWNER/REPO`，否则前端禁用评论提交（§4.7.4）。
